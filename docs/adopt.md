# Adopting parity in the consuming repo

The consuming repo is the one that will hold the new implementation (the Angular app, say). Nothing
below touches the legacy repo.

## Layout in the consuming repo

```
legacy/
  extract.config.json           skeleton from the detected csproj; yours to edit (Steps, 2)
  control-categories.json       from templates/, extended with custom controls
  .phase                        extract | map | specify | implement | bug   (read by the hooks)
  hooks/guard-legacy.sh         from adopt/hooks
  hooks/lint-on-stop.sh         from adopt/hooks
  templates/                    the kit's templates (spec.md, fixture.json, evidence.json, extractor-debt.md, ...)
  run-phases.sh                 only with --phase-driver: one fresh headless session per phase
  <Module>/
    manifests/<Form>.json, .md  generated by parity extract (.prev.json: the one before the last change)
    module.json
    fixtures/<name>.json        recorded service calls
    evidence/<Form>.json        written by parity evidence add; quoted legacy lines specs cite as ev:
    registry/                   scenarios.json, decisions.json, dependencies.json (map phase, see below)
    spec/<Form>.md
    extractor-debt.md           only when raw/diagnostics exist
.claude/
  settings.json                 hooks wired (the hooks block of adopt/.claude/settings.json, merged)
  skills/parity-*/SKILL.md      from adopt/.claude/skills
  skills/parity-specify/spec.md the spec template, next to the skill that starts from it
```

## Setup: `parity init`, then `parity doctor`

Put the `parity` binary on PATH (a release zip, or `bin/publish.sh win-x64` in the parity repo), or set
`PARITY_BIN` to its path: the skills and the stop hook call `"${PARITY_BIN:-parity}"`. On Windows use Git Bash
for every command here; the hooks are POSIX `sh`. Nothing else is needed from the parity repo: the kit
(skills, hooks, settings block, templates) is inside the binary.

```
parity init [--merge] [--project <legacy.csproj>] [--module <Name>] [--phase-driver]
parity doctor [--config <extract.config.json>]
```

Run both from the root of the consuming repo.

**`parity init`** lays the layout above out. Which file goes where is read from the kit (`adopt/kit.json`,
embedded), so a new skill, hook or template in a later release arrives with the next `init`, no new steps.
Every line it prints says what happened to one path:

| Line | Meaning |
|---|---|
| `create` | the file was missing and is now written |
| `unchanged` | the file is already what the kit has |
| `skip` | the repo's own file (`legacy/extract.config.json`, `control-categories.json`, `.phase`): written once, never touched again |
| `would-update`, `would-merge` | a kit file differs, or `.claude/settings.json` lacks parity's hooks: nothing was changed, exit 1. `--merge` applies it |
| `update`, `merge` | `--merge` rewrote the kit file / added the hooks |

- **settings.json.** With `--merge`, parity's hook entries are appended to each event's array **after** the
  repo's own, which keep their order and content; permissions and every other key stay as they are. A hook the
  repo already wires (same command, or the same script) is not added twice, and a different matcher on it is
  left alone (`doctor` warns). A `settings.json` with comments (or trailing commas) is read, but never rewritten:
  while it lacks something of the kit's, `init` names what and stops before writing anything, so add those
  entries from `adopt/.claude/settings.json` by hand and run `init` again. Without a `settings.json`, the kit's is written.
- **Skills.** Only `parity-*` folders are installed. The repo's own skills are not touched. The specify skill
  starts from `.claude/skills/parity-specify/spec.md`, a copy of `templates/spec.md` next to it, and every
  skill calls the binary as `"${PARITY_BIN:-parity}" <command>`: `PARITY_BIN` when set, else `parity` on PATH.
- **Config skeleton.** `--project` names the legacy csproj; without it the one csproj in the repo (outside
  `bin`, `obj`, `legacy`) is used, and with none or several the `project` key keeps its placeholder and `init`
  says so. From the csproj it fills `project`, `selfAssembly`, `referenceDirs` (its `OutputPath`) and sets
  `includeRuntimeReferences` (false for a .NET Framework project, with the `v4.x` Reference Assemblies globs).
  `serviceBoundary` and `variants` are emptied: they are the adopter's decision. The file stays strict JSON, which
  the guard's `jq` needs.
- **Tool-owned files** (skills, hooks, templates, the driver) are overwritten only by `--merge`, so a hook you
  edited is reported, not lost. **Repo-owned files** are never overwritten.
- `--module <Name>` also creates `legacy/<Name>/spec/` and `legacy/<Name>/fixtures/` (with a `.gitkeep`).
- A second `init` changes nothing and exits 0; it exits 1 only while something waits for `--merge`.

**`parity doctor`** prints one line per check, `pass`, `warn` or `fail`, and exits 1 when any check fails.

| Check | Fail | Warn |
|---|---|---|
| `.net sdk` | - | no 10.x SDK (not needed with a release binary) |
| `parity binary` | `PARITY_BIN` is not a file and not on PATH, or neither it nor `parity` is set up | - |
| `sh`, `jq` | not on PATH (`jq` missing makes the guard refuse every call in specify and implement) | - |
| `config` | missing, unparseable, or not strict JSON | - |
| `legacy root` | `PARITY_LEGACY_ROOT` set to a missing directory, or unset with no `project` | unset, and the project's folder is not on this machine |
| `legacy project` | `project` empty or not found | - |
| `reference assemblies` | a `references` folder does not exist; .NET Framework project with an empty list | .NET Framework project with `includeRuntimeReferences` true |
| `output path` | the csproj's `OutputPath` folder does not exist (the project is not built) | no `OutputPath` |
| `built` | `selfAssembly` (or the project's own DLL/EXE) does not exist | nothing to look for |
| `references` | - | more than 200 DLLs resolve (minutes per run behind an antivirus), or some referenced DLLs are not found |
| `skills`, `hooks`, `templates`, `spec template` | a file `init` installs is missing | a file differs from this parity's kit |
| `hook <Event> <script>` | not wired in `settings.json`, or its script is missing | wired with a different matcher than the kit's |
| `phase` | `legacy/.phase` is not a phase of the kit | missing |
| `git ignore` | `legacy/`, a module folder or `.claude/` is ignored (and untracked) | not a git work tree |

**`--phase-driver`** writes `legacy/run-phases.sh` (on Windows, run it with the Git for Windows `sh` the hooks
already need): each phase of the kit is started as its own
headless agent process (`claude -p`, or `PARITY_AGENT`), after `legacy/.phase` is set, with that phase's prompt.
`sh legacy/run-phases.sh <Module> <Form> [phase ...]` runs the given phases, default every driven one in order.
Pick the phases to fit the work a person does in between (recording fixtures after `extract`, the review after
`specify`): for example `extract`, then record, then `map` and `specify`. A failing session stops the run. `bug` is not driven: it starts from a report.

## Steps

0. `parity init`, then `parity doctor` (above); fix every `fail` before going on.
1. `parity probe <csproj> --forms '<Form>'` on the work machine. Read the shapes list once. Anything
   that is not an assignment, a `+=`, an `Add`/`AddRange`, a `DataBindings.Add`, `SetValidationRule`,
   `ApplyResources`, or a `BeginInit`/`SuspendLayout` family call will show up in `raw`.
2. Check and complete `legacy/extract.config.json` (`init` filled what the csproj determines). The service boundary is the decision that matters most; everything
   behind it is a `svc:` id that fixtures and rules hang off. For a .NET Framework project set
   `includeRuntimeReferences` to `false` and put the `Reference Assemblies\...\.NETFramework\v4.x`
   folder (and its `Facades`) first in `references`; the tool's embedded .NET 10 references are for
   .NET Core-era projects only, and mixing the two makes `System.Object` ambiguous. `TYPE-UNRESOLVED`
   diagnostics on framework types mean this is wrong.
3. `parity extract --config legacy/extract.config.json --module <Module> --forms '<Form>'` for one
   small form. Read the summary: `raw` and `diag` should be 0. If not, either the config is missing a
   reference (`TYPE-UNRESOLVED`, `REF-MISSING`, `BASE-UNRESOLVED`) or the extractor has a hole: file an
   issue with `parity report <manifest.json>` and the probe shapes, and acknowledge the entries in
   `extractor-debt.md` meanwhile. Never quote the manifest's Raw or Diagnostics sections directly;
   they carry real identifiers.
   When some tenants get a customised subclass of a form instead of the form, list them under `variants`
   (one entry per tenant family; see `templates/extract.config.json`): `id` names the variant in specs,
   `subclasses` the class names to describe, `project` and `selfAssembly` the variant's csproj and built
   assembly when it lives outside the module's project (`subclasses` then defaults to every subclass of a
   module form found there). `factories` names factories to read when the tool does not find them itself:
   a type, or `Type.Method`, simple or namespace-qualified. The log prints `variant <id>: <class> on <form>`
   per variant, listing each subclass found; a `VARIANT-CONFIG` diagnostic means an entry could not be applied.
4. Commit the manifests. They are generated, deterministic, and the thing specs bind to.
5. Record fixtures for every id in `module.json` `serviceCalls` with your own runner, one file per
   recording, `service` and `recorded` set. An outcome the host cannot be made to return is a synthetic
   fixture: `parity fixture scaffold <svc-id> --from <recorded.json> --variant <outcome>` writes a
   labelled copy to edit into that reply (`docs/spec.md`, Fixtures). Quote the legacy facts a rule will
   need that the manifest lacks with `parity evidence add <Form> <file>:<start>-<end> --note <text>`
   (the file relative to the legacy root; `--config` defaults to `legacy/extract.config.json`). It reads
   `legacy/.phase` and refuses in `specify` and `implement`: the agent there may cite evidence, not
   collect it.
6. Set `legacy/.phase` to `map`, fresh session, `parity-map` skill (`sh legacy/run-phases.sh <Module> <Form> map`
   does both): the agent reads the legacy source and the manifests and records the module's context in
   `legacy/<Module>/registry/` (next section). The stop hook runs `parity registry check legacy/<Module> --gate`
   and refuses the turn while it is red.
7. Set `legacy/.phase` to `specify`, start a fresh agent session, run the `parity-specify` skill for
   the form (`sh legacy/run-phases.sh <Module> <Form> specify` does both when `init --phase-driver` wrote it). The hook denies anything outside the consuming repo in this phase; the agent works from
   `manifests/<Form>.md` and `evidence/<Form>.json`. Iterate until `parity lint` is green. The linter
   itself reads the legacy source to re-hash every cited `ev:` record (`EV-STALE` when it moved): the
   guard constrains the agent, not the tool, so the legacy root must be reachable where lint runs
   (`PARITY_LEGACY_ROOT` overrides the path recorded in the evidence file). Review the spec against the
   running legacy app. Set `status: reviewed`.
8. Set `.phase` to `implement`, fresh session, `parity-implement` skill. The agent gets the spec, the
   fixtures and your scaffold; tests are named with rule ids; the stop hook runs
   `parity lint --gate --implement <dir>`.
9. A bug report goes through `parity-bug`: locate the control id, classify, land the fix as a test, a
   spec line or an extractor issue.

## The map phase and the registries

A manifest describes one unit. What lies between units does not fit in one: the values a host hands a
unit and reads back, the session or cache fields several units share, which unit embeds which, what a
service answers when it fails, and which business scenarios are worth testing. The extract records the
structural half in each manifest (Contract, Shared state, Units this unit opens; `docs/manifest.md`) and
in `module.json` (`sharedState`, `composition`, `dependencies`). The map phase records the half that
needs a reader, in three files under `legacy/<Module>/registry/`:

| File | Entries | Required fields |
|---|---|---|
| `scenarios.json` | `scn:<words>` | `id`, `version`, `title`, `role`, `rights[]`, `negative`, `exercises[]` (manifest ids), `cite[]`; `lastVerified` (YYYY-MM-DD) once run against the host |
| `decisions.json` | `dec:<words>` | `id`, `question`, `answer`, `owner`, `date` (YYYY-MM-DD), `cite[]` |
| `dependencies.json` | one per `svc:` id of `module.json` | `id`, `errors[]` of `{ case, reply, fixture | cite[] }` |

Each file also carries `"module": "sha256:<16 hex>"`, the extract revision it was reviewed against (one
hash over every manifest's hash). The schema is closed: a field outside the lists above is
`REGISTRY-INVALID`, so a scenario cannot carry a policy number or a client name. `role` and `rights` are
lowercase tokens (`agent`, `policy.edit`). Rules name a scenario as `scn:<id>@<version>` under
`- scenarios:` and a decision as `decided-by dec:<id>` or `closed by decision dec:<id>` (`docs/spec.md`);
a fixture names its scenario in `scenario`.

| Command | What it does |
|---|---|
| `parity registry init <module-dir>` | writes the three files, `dependencies.json` seeded with every `svc:` id; never overwrites |
| `parity registry check <module-dir> [--gate]` | the findings in `docs/lint.md`, Registry; `--gate` turns unreferenced and unverified scenarios into errors |
| `parity registry stamp <module-dir>` | records the current revision in each file; refused while check has an error other than `REGISTRY-STALE` |
| `parity registry query <module-dir> [--touches <id>] [--role <r>] [--right <r>] [--negative\|--positive] [--unverified]` | the matching scenarios, with the fixtures that name them |
| `parity registry catalog <module-dir> [--out <file.md>]` | per service: signature, request and reply templates, callers, error cases, fixtures with provenance (recorded date and environment, or synthetic) |

In `map` the guard lets every tool read, the legacy source included, and lets `Edit`, `Write`,
`MultiEdit` and `NotebookEdit` write only under `legacy/<Module>/registry/` and `legacy/<Module>/evidence/`
("map phase writes only legacy/<module>/registry/ and legacy/<module>/evidence/" otherwise). A shell
command can still write; the stop hook is the net: it refuses to end a map turn that changed files
outside those two directories (the kit's `legacy/hooks/`, `legacy/templates/` and the files directly in
`legacy/` excepted). `parity evidence add` works in `map` as in `extract`, so a registry entry
can cite an `ev:` record. `specify` and `implement` keep the legacy tree unavailable exactly as before.

**Accumulation protocol.** The registries grow with every pass and are never rebuilt from scratch:

1. A pass is not done until the registries are updated. After an extract that changed a manifest the
   revision moves and every registry file is `REGISTRY-STALE`; `parity lint --gate` on any spec of the
   module fails on it too. The extract log prints `changed: <Form>` per changed manifest, `stale spec:`
   per spec bound to it, and `registry: STALE` when the module has a registry. The stop hook decides from
   the state of each module that has a `registry/`, not from the uncommitted diff, so committing first does
   not hide a stale registry. In `extract` a stale registry never blocks the stop (the extract agent cannot
   review it): the hook names the stale modules and says to run the map phase next. In `map`, `specify` and
   `implement` a stale registry blocks the stop with `REGISTRY-STALE` until map has reviewed and stamped it.
2. Review: `parity diff manifests/<Form>.prev.json manifests/<Form>.json` per changed form, then each
   scenario, decision and dependency entry that cites an id in it. Specs move with `parity rebind`.
3. `parity registry stamp` once check is green.
4. A human answer is a decision entry with an owner, a date and a citation, recorded by the agent from
   what the human said. Specs then point at it instead of restating it.

## Why the hooks are not optional

A skill is prose. The agent that reads "do not open the legacy repo" will open it when the manifest
is unfamiliar and the legacy file is one `Read` away. `guard-legacy.sh` makes the legacy path
unavailable during specify and implement (next section); `lint-on-stop.sh` refuses to end a turn with a
red spec. Both are a few lines of shell reading the hook's JSON from stdin.

## The guard hook

`guard-legacy.sh` is a PreToolUse hook. In `extract` and `bug` it does nothing; `map` is described above. In `specify` and
`implement` it works as an **allow-list**: a tool call may only touch the consuming repo (the directory
the hook runs in) minus the legacy source root, plus the directories in `guard.allowRoots`. The manifests,
specs, fixtures, evidence and scaffold are all inside the repo, so they need no entry. The legacy root
is `PARITY_LEGACY_ROOT`, else the directory of `project` in `legacy/extract.config.json`; it is always
refused, even when an allowed root contains it.

| Tool | What is checked |
|---|---|
| `Read`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit` | the file path, resolved against the `cwd` in the hook input, must be allowed |
| `Grep`, `Glob` | the search path (the `cwd` when omitted) and the glob up to its first wildcard segment must be allowed, and the search root they make must not contain the legacy root (`Grep` with no path, `.` or `**/*.cs` from a repo that holds it is refused: narrow the path to a directory outside it); a `..` after a wildcard segment and a brace alternative that can stand for `..` (`{..,x}`, `{.?,x}`) are refused, `*.{ts,tsx}` is fine |
| `Bash`, `PowerShell`, `Monitor` | the `cwd`; every path-like token (contains `/` or `\`, is `.` or `..`, a drive path), also when glued to a short option (`-I../x`); a `cd`, `pushd`, `Set-Location` and friends as the first word of a command must stay inside the allowed roots, and later relative paths resolve from there. A command starts after `;`, `|`, `&`, `(`, `)`, `{`, `}` or a newline outside quotes, and after a reserved word (`then`, `do`, `else`, `elif`, `if`, `while`, `until`, `!`, `time`) or a wrapper (`command`, `builtin`, `env`, `exec`, `VAR=x`). The quoted argument of `sh`/`bash`/`zsh`/`dash`/`ksh`/`powershell`/`pwsh` `-c`/`-command` and of `eval` is a command of its own, and its `cd`, like one in a `( )` subshell, ends with it. Option words before `-c` (`--norc`, `--login`, `-o pipefail`) do not change that. A `cd` word anywhere else that is followed by a path, a variable (`$HOME`, `%USERPROFILE%`) or nothing refuses the call, unless it is an argument of `echo`, `git` or `printf`. A word without a separator that names the legacy root from the `cwd` (`ls LegacyApp` with the root inside the repo) is refused too. Each path segment is judged: a segment a wildcard or a quote/backslash splice can turn into `..` (`.''./x`, `.\./x`, `.?/x`, `.*/x`, `[.]*`), a `..` after a wildcard segment (`src/*/../..`), unquoted brace expansion, `~` and `$VAR/...` cannot be resolved and are refused. Other wildcards (`src/**/*.ts`), regexes (`s/a.*b/c/`, `[a-z]+`), quoted arguments (`grep -E "[0-9]{2,4}"`) and MSBuild switches (`/p:Configuration=Release`, `/t:Rebuild`) are fine; the path is checked up to its first wildcard segment |
| `mcp__*` | refused when the tool name matches the deny-list (below); otherwise every string value in the input that contains `/` or `\`, or is `.`, `..`, `~` or empty (read as `.`), must be an allowed path that does not contain the legacy root, and any other value must not name the legacy root from the `cwd` |
| anything else | refused: the hook cannot decide |

Paths are compared case-insensitively with `/` and `\` equal and `C:\x`, `/c/x`, `/mnt/c/x` and
`/cygdrive/c/x` the same place. After those checks the legacy root is also searched for anywhere in the
input as a whole path (followed by `/`, a quote, whitespace or the end), which catches a root named in the
input of a tool the hook does not parse; a sibling such as `<root>-next` is not a match.

**Where it runs.** The settings start the hook as `sh "$CLAUDE_PROJECT_DIR"/legacy/hooks/guard-legacy.sh`
and the script changes into `$CLAUDE_PROJECT_DIR` (else its own cwd) before it reads `legacy/.phase`, the
config and the log. Claude Code sets the variable for hook commands; keep it in any hand-merged entry, or a
session that `cd`s below the repo root cannot find the script or the phase. If the variable names a missing
directory the call is refused.

**Fail closed.** If the hook cannot decide in a restricted phase it exits 2 with a one-line reason: root
unknown, input not JSON, no path in a path tool's input, unresolvable `cd`, unknown tool, unreadable
`guard` settings, a `legacy/extract.config.json` that is not strict JSON, **or no `jq`**. The hook reads the
config with `jq`, so keep it free of the `//` comments and trailing commas parity itself accepts; the refusal
says so when it finds them, even with `PARITY_LEGACY_ROOT` set. `jq` is required to read tool input; the `sed`
fallback only finds the legacy root so the message can say what is wrong. Install it with
`winget install jqlang.jq`, `scoop install jq`, `brew install jq` or `apt install jq`.

**MCP code-index servers.** A code-search or code-graph server that indexes the legacy tree usually takes
no path, so no path check can see it. The hook refuses MCP tools by name instead. Built in, matched
case-insensitively against the full `mcp__<server>__<tool>` name (`?` is any one character): `*code?index*`,
`*codeindex*`, `*code?graph*`, `*codegraph*`, `*code?search*`, `*codesearch*`, `*codebase*`, `*repo?map*`,
`*repomap*`, `*symbol*`, `*semantic?search*`, `*serena*`, `*sourcegraph*`, `*tree?sitter*`, `*treesitter*`,
`*ast?grep*`, `*lsp*`, `*language?server*`, `*roslyn*`, `*ctags*`, `*cocoindex*`, `*gitnexus*`,
`*graphify*`, `*claude?context*`, and Graft, the tree-sitter code-graph server (`mcp__graft__*` for its
server name, `*__graft_*` for the `graft_` tool prefix). Add your own in `legacy/extract.config.json`:

```json
"guard": {
  "denyTools": ["mcp__house-index__*"],
  "allowRoots": ["../../shared-fixtures"]
}
```

`allowRoots` entries are relative to the config file (`legacy/`) or absolute. The cleanest fix for an
index server is still not to register it in the consuming repo's MCP config for these phases.

**Matcher per platform.** The hook only sees the tools the `matcher` in `.claude/settings.json` selects:

| Platform | Shell tool | Covered by |
|---|---|---|
| macOS, Linux, Windows with Git Bash | `Bash` | the shipped matcher |
| Windows with the native PowerShell tool enabled | `PowerShell` | the shipped matcher |
| any, long-running watchers | `Monitor` (takes a `command`) | the shipped matcher |
| any, MCP servers | `mcp__<server>__<tool>` | `mcp__.*` in the shipped matcher |

The shipped matcher is `^(Read|Grep|Glob|Bash|PowerShell|Monitor|Edit|Write|MultiEdit|NotebookEdit|mcp__.*)$`.
If your Claude Code version names a tool differently, or adds another shell or file tool, add it to the
matcher; a tool the matcher does not select is never checked. A name the matcher selects but the hook does
not know is refused. The hook command itself runs under `sh` (Git Bash on Windows) on every platform.

**Proof.** Every denied call appends one tab-separated line to `legacy/.guard-denials.log`: UTC date,
phase, tool, reason. The reason carries the resolved path or the tool name. Keep it with the run's
evidence: after a cooperative run an absent or empty file means the agent never asked for the source
through a guarded tool. It is not tamper-proof: the log, `legacy/.phase`, the hook and
`.claude/settings.json` live in the allowed repo root, and an agent that rewrites or deletes them is outside
what a PreToolUse hook can prevent.

**Limits.** This is a guard for a cooperative agent, not a sandbox: it does not follow
symlinks or junctions, cannot see inside a script or program the agent runs, and does not expand shell
variables or command substitutions. It reads a command as tokens, so what a program does with a name it was
handed (a tool that opens its own wildcards, a path assembled by `eval` or `xargs`) is outside it, and a
token that starts with `\` (a drive-rooted Windows path or a regex escape) is not resolved. A command string
handed to a program other than the shells above (`su -c`, `watch`, `ssh`) is read as plain arguments. With the
legacy root inside the repo, `Grep`, `Glob` and MCP searches rooted above it are refused, but a shell recursive
search or wildcard over a directory that contains it (`grep -r Foo .`, `cat */Forms/X.cs` from the repo root)
reaches it without naming it, which token checks cannot catch. Prefer the layout with the legacy tree beside the
repo, not inside it: with the legacy root inside the repo, every repo-wide `Grep`, `Glob` or MCP search is refused in
the restricted phases. A `cd` is followed as if it ran unconditionally and succeeded: a conditional
(`false && cd src`, `cd src || ...`), backgrounded (`cd src &`) or piped (`cd src | ...`) `cd`, a `cd` that
fails, and `popd` are not modelled, so a later relative path may resolve elsewhere than the guard thinks. An
MCP server with its own index of the legacy tree takes no path, so only its name can refuse it. Neither the
log, `legacy/.phase`, the hook nor the settings are protected from the agent (see Proof).
Enforce a hard guarantee with file permissions or a separate machine user.
